### Required steps explained in more detail
**Step 6** - In step 3, I made a change directly in user.py on GitHub, and in step 4 I made a different change on the same line in user.py locally. Because of this, my local develop and the develop on GitHub weren't aligned anymore, and that is why I couldn't push to the develop branch. And then when I pulled (fetch + merge), a conflict appeared. To fix this, in GitKraken's conflict editor I kept both changes, so the constructor now sets both the username and the bio. I committed the merge, took a screenshot of the resolved tree, committed it, and pushed. This could have been avoided if I had pulled before making the next change, or if I didn't commit to the same branch from two places.

**Step 19** - In step 16 I committed my change with the message "Some changes", as requested in the task, and opened a PR to develop. In step 18, as a reviewer, I explained that this message doesn't describe what was changed or why, which goes against commit message best practices. To fix this, I created a new branch called feature/step-4-update from feature/step-4 and changed the commit message to "Add User example to main_runner.py". I pushed it, opened a new PR to develop (#20), reviewed and merged it. I closed the old PR, so the commit with the bad message couldn't be merged by mistake. I created a new branch instead of fixing it on feature/step-4, because that branch was already pushed, and changing its commit would need a force push, which rewrites history. This way the original branch stays as it was, and the fix is visible as a separate, clean PR.

**Step 21** - The task asked to deliver all production-ready code to the customer as version 1. First, I created a release branch called version-1 from develop. Then I merged it into master with a merge commit, tagged that commit as v1, and pushed both master and the tag to GitHub. Normally the release branch would also be merged back into develop, but since I didn't make any extra commits on it, develop already had everything and there was nothing to merge back. I left the step-3 PR (#18) out of the release, because it was still waiting for review, so it wasn't ready for production. I did it this way because in Gitflow, master should only contain released, production-ready code, and the tag marks exactly which version was delivered.

**Step 22** - After the release, the customer asked for a new feature: a `__str__` method in the User class. Since this is something new and not a bug in production, I created a feature branch, feature/step-22, from develop, and added the method there. While I was still working on this feature, the production bug from step 23 came up, so I fixed that first. Once the hotfix was done, I merged develop into feature/step-22 to bring in the fix, then opened a PR to develop (#21) and merged it. In Gitflow, new features are built from develop and go out with the next release, while hotfix branches are only for urgent production bugs.
